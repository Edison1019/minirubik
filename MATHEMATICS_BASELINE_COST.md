### Mathematical state space and HTM diameter

Let $G=\langle R,B,D\rangle$ be the group generated by quarter-turns of the right, back, and down faces. These moves fix the front-upper-left corner in both position and orientation. The state model therefore records the other seven corners. This is the fixed-corner group, rather than a graph formed by taking arbitrary face moves and identifying states under whole-cube rotations.

There are $7!$ possible arrangements of the seven movable corners. Their orientations take values in $\{0,1,2\}$ and satisfy:

$$
\sum_{i=0}^{6}o_i\equiv0\pmod3.
$$

Only six orientations are independent, giving $3^6$ possibilities. Thus the candidate state space has size:

$$
7!\times3^6=5040\times729=3{,}674{,}160.
$$

Counting these valid encodings alone does not prove that all of them are reachable using R, B, and D. The baseline's exhaustive BFS supplies that check: `build_table()` rejects the result unless its final discovered-state count equals `STATES`. It reaches all 3,674,160 encodings from the solved state. Consequently, the fixed-corner group represented by these states has order $|G|=3{,}674{,}160$.

The Cayley graph has one vertex for each group element and edges corresponding to the generating set:

$$
S=\{R,R^2,R^{-1},B,B^2,B^{-1},D,D^2,D^{-1}\}.
$$

This set is inverse-closed, so every move can be undone and edges can be viewed as undirected. In the half-turn metric, all nine moves have cost one, including $R^2$, $B^2$, and $D^2$. BFS from the identity (the solved cube) therefore discovers states in increasing optimal HTM distance. The inverse of the discovery move is stored for each newly reached state, giving a step back toward the preceding BFS layer.

The independent baseline oracle gives the following complete distance distribution, also recorded by the full H3 checker:

| Optimal HTM distance | Number of states |
| ---: | ---: |
| 0 | 1 |
| 1 | 9 |
| 2 | 54 |
| 3 | 321 |
| 4 | 1,847 |
| 5 | 9,992 |
| 6 | 50,136 |
| 7 | 227,536 |
| 8 | 870,072 |
| 9 | 1,887,748 |
| 10 | 623,800 |
| 11 | 2,644 |
| Total | **3,674,160** |

The 2,644 states in layer 11 prove that the maximum distance from solved is at least 11. Complete enumeration with no deeper layer proves that it is at most 11. Since Cayley graphs are vertex-transitive, distances between arbitrary vertices reduce to distances from the identity, so the graph's HTM diameter is exactly **11**. Testing only a few examples would establish neither complete coverage nor this upper bound.

The orientation constraint is a modulo-3 invariant, not a parity condition. For example, twisting a single movable corner by one or two units while leaving the others unchanged violates it and cannot result from legal moves. Two nonzero twists can satisfy it if their sum is zero modulo 3. There is also no requirement that the corner permutation be even: a quarter-turn cycles four corners and is an odd permutation.

### Baseline memory and computational cost

The baseline constructs a full BFS table before answering a query. Its three dominant allocations are:

| Allocation | Storage | Calculation | Bytes |
| --- | --- | --- | ---: |
| `toward_solved`: one move per state | Heap | $3{,}674{,}160\times1$ | 3,674,160 |
| BFS queue of 32-bit state ranks | Heap | $3{,}674{,}160\times4$ | 14,696,640 |
| Factored quarter-turn transitions | Automatic | $3\times(5040+729)\times2$ | 34,614 |
| Dominant-allocation peak | | | **18,405,414** |

These allocations coexist during table construction. Their total is approximately **17.553 MiB**. It is the exact sum of these three allocations, not a complete process-memory measurement: small local variables, allocator overhead, code, and other runtime storage are additional. The queue alone accounts for approximately 79.8% of this total, and the full-state move table accounts for approximately 20.0%. The queue is freed after construction, but the move table remains while answering the query.

Each of the 3,674,160 states is expanded once, with nine HTM successors:

$$
3{,}674{,}160\times9=33{,}067{,}440
$$

directed edge examinations. Each successor requires one permutation-table update and one orientation-table update, giving:

$$
33{,}067{,}440\times2=66{,}134{,}880
$$

transition updates during the BFS expansion. This excludes transition-table generation, table initialization, queue operations, visited checks, and loop control. The quarter-turn tables generate the three powers of each face incrementally, so each HTM successor needs one additional paired transition.

Using the measured ratio of approximately 48 host bytes per guest byte, the dominant guest-memory peak projects to roughly **842.5 MiB of additional host memory**. Applying the measured simulation rates to the assignment's approximate $10^9$-instruction estimate projects about **66.6 seconds** on RV32_ISS and **119.4 minutes** on RV32_5S. These are projections, not a measurement of the full baseline on Ripes; actual instruction mix and allocation behavior may change the result.

The baseline's strength is that, after this construction cost, solving a query needs at most 11 table-guided moves. On Ripes, however, the construction strategy exceeds the 128 KiB static-data budget by a wide margin, and a full-state distance table is explicitly excluded by the precomputation rule. Moving to small abstract tables and target-side search addresses these constraints while preserving optimality, as discussed in the next stage.
